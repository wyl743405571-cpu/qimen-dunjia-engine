# Verification Suite — 可复现的实测脚本

这个目录里的每个脚本都对应本站或本引擎公开页面上引用过的一个数字。
**所有数字都可以由你本人在本地跑出来**，不需要相信我们。

设计上刻意遵守两条规则：

1. **断言必须可能失败。** 引擎开发过程中出现过"检查地盘是否有庚"这类规则——
   庚是六仪之一，永远在地盘上，所以那条规则恒为真、恒真等于没写。
   本目录所有断言都经过"确认它真的会红"这一步。
2. **测试预期写错 ≠ 代码错。** 多个脚本的初版断言是我们自己算错，
   逐条核对真实设计后才改对的。脚本里对阈值都写了注释说明为什么是这个值。

## 怎么跑

```bash
npm install                       # 只有一个依赖：lunar-javascript
node verify/sweep_coverage_v2.js 2000 2050    # 全量遍历
node verify/measure_divergence.js 30           # 分歧率
node verify/measure_geju.js 10                 # 格局覆盖率
node verify/check_beige2.js                    # 单条罕见格局的可达性
node verify/audit_book_cases.js                # 书载案例库审计
```

引擎默认从仓库内 `src/index.js` 载入。如果你想测一份独立的引擎副本：

```bash
ENGINE_PATH=/path/to/engine.js node verify/sweep_coverage_v2.js 2000 2050
```

案例库审计脚本默认读本目录下的 `book_case_library_tagged.json`，
也可以指向别处：

```bash
CASES_PATH=/path/to/book_case_library_tagged.json node verify/audit_book_cases.js
```

## 1. sweep_coverage_v2.js — 全量遍历与引擎不变式

**实测结果（已上线，页面上引用了同一组数字）**

| 指标 | 数值 |
|---|---|
| 排盘总次数 | **44,064** |
| 崩溃 | **0** |
| 五条不变式违反 | **0** |
| 耗时 | 64.5 秒 |

遍历范围：2000–2050，每年的 3 个代表日 × 12 时辰 × 2 种定局法。

被检查的五条不变式：

- `A_struct` — 盘面结构完整（天地盘各 9 宫、九星缺中宫、八门八神齐全）
- `B_zhiFuXing` — **值符星必落值符宫**（值符落中五宫时走寄坤分支，单独判定）
- `C_zhiShiMen` — **值使门必落值使宫**
- `D_zhiFuZhiShi` — 值符星与值使门的宫位关系自洽
- `E_plateRange` — 宫位取值恒在 1–9

> **一个诚实的说明**：这一条只能证明"实现与规则一致"，
> **不能**证明"这套规则符合古法"。前者是我们能测的，后者需要文献考据。

### 这里踩过的坑，值得写下来

第一版脚本报告「864 次结构异常」——是我们把字段名写错了，
引擎的真实字段是 `tp`/`dp`/`xing`/`men`/`shen`，不是我们假设的名字。

修完之后又报「713 次值符星落宫错误」。这次是**断言错，引擎是对的**：
`xing[宫]` 可能存合并标记 `"天芮,天禽"`（天禽寄坤随天芮），不能精确相等；
而且 `zhiFuXing` 指的是**原宫**的星，落盘之后才叫值符星。

逐宫打印核对后确认引擎完全正确。如果当时图省事去"修引擎"，
就会把一个正确的引擎改坏。

## 2. measure_divergence.js — 定局法分歧率

**实测结果**

采样2000–2029，12,960 个时刻，拆补 vs 置闰逐盘对比：

| 指标 | 数值 |
|---|---|
| 九宫盘面不同 | **41.6%** |
| 局数不同 | 40.4% |
| 值符宫不同 | 41.0% |
| 值使宫不同 | 40.9% |
| 八宫全不同 | **41.1%** |
| 完全相同 | 58.4% |

**为什么这个数字重要**：如果你用某个App 排盘，另一个 App 排出来不一样，
大概率不是谁算错了，而是两边用了不同的定局法。这个数字给出了这种情况的**先验概率**。

它同时也是我们不把"拆补"和"置闰"藏起来只给你一个结果的原因。

## 4. check_beige2.js — 罕见格局的可达性

「悖格」在 measure_geju里只命中 0.15%。这类低命中率有两种可能：
真的极罕见，或者判定条件写错了。这个脚本专门区分这两种情况。

**实测结果**

- 理论条件（值符宫天盘丙 + 地盘戊）满足数：**39**
- 引擎实际输出悖格数：**39**
- 命中率：39 / 25,920 = **0.150%**

**两者逐盘完全一致** —— 说明判定逻辑无误，它只是罕见但可达，不是死规则。

## 5. audit_book_cases.js — 书载案例库审计

数据源：142 例从《神奇之门》《开悟之门》等书里蒸馏的案例，含出处页码。

**实测结果**

| 指标 | 数值 |
|---|---|
| 案例总数 | **142** |
| 有出处页码 | 136（**95.8%**） |
| 盘面可计算 | 132 / 142（93%），10 例资料不足 |
| 局数可比对（拆补） | 97 例 |
| **局数匹配（拆补）** | **63 / 97 = 64.9%** |
| 局数可比对（置闰） | 94 例 |
| **局数匹配（置闰）** | **40 / 94 = 42.6%** |
| 有预期吉凶判定 | 51 例（35.9%） |

**两个必须一起说的发现：**

**一、拆补明显优于置闰。** 在同一批 94 例两法都可测的案例里，
两派结论一致 70 例、不一致 **24 例**（例如《开悟之门》p234书载阴4局，
拆补得阴遁4、置闰得阴遁6）。这构成我们默认采用拆补的实证依据，
而不是"某派这么说的"。

**二、我们必须承认的短板。** 142 例里只有 51 例带预期吉凶判定，
其中 **45 例来自 OCR 自动提取、标注为 needsReview（需人工核对）**。
换句话说：**这些预期结果尚未全部人工校核，暂不应作为回归基线使用。**

我们把这件事写在这里，而不是藏起来——一个声称"可验证"的库，
如果悄悄拿未经核对的OCR 结果当准确率，那是自我欺骗。
